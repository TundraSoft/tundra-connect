# 📐 Conventions

This is the coding standard for every connect in this repository. It exists so
that a contributor can move between connects without re-learning structure,
and so that generated tooling (`.github/scripts/workspace.ts`) can rely on a
predictable shape.

## Repository layout

Every connect lives under `connectors/<name>/` (`connectors/openexchange/`,
`connectors/twilio/`, ...), mirroring TundraLibs. `deno.json`'s `workspace`
and `package.json`'s `workspaces`/`test:bun`/`test:node` are a static
`connectors/*` glob — they never need regenerating when a connect is added or
removed. What still can't be globbed (per-connect labels, release-please
package config, issue-template dropdowns, README's connect list) is
generated by `.github/scripts/workspace.ts`, the single source of truth for
those files; never hand-edit the generated sections.

## Connect (connector) layout

```
connectors/<connect>/
├── deno.json            # @tundraconnect/<connect>, exports map
├── package.json          # mirrors deno.json exports for Bun/Node
├── mod.ts                 # single re-export site (client + schemas + errors)
├── README.md               # main docs and wiki page
├── CHANGELOG.md           # release-please generated — never hand-edited
├── <Connect>.ts            # main client class, PascalCase
├── <Connect>.test.ts       # tests sit next to the source they cover
├── errors/                # error class + error-code registry (see below)
│   ├── Base.ts
│   ├── <Connect>ErrorCodes.ts
│   ├── Base.test.ts
│   └── mod.ts
├── schema/                # Guardian request/response schemas
│   ├── <Thing>.ts          # one schema object + inferred type per file
│   ├── <Thing>.test.ts
│   └── mod.ts              # barrel — re-exports every schema + type
└── docs/                  # prefixed topic docs published to the wiki
  ├── <Connect>-API.md
  ├── <Connect>-Errors.md
  └── <Connect>-Schemas.md
```

- A connect's root `README.md` is its main documentation and wiki page.
  Supplemental docs in `docs/` are named `<Connect>-<Topic>.md`, where
  `<Connect>` is its workspace display name; no `docs/README.md` is created.
- One class/schema/error-registry per `PascalCase.ts` file. Barrels
  (`mod.ts`) are the only files allowed to just re-export.
- Cross-folder imports go through the folder's `mod.ts` barrel
  (`from './schema/mod.ts'`); same-folder siblings import directly.
- A connect's public surface is exactly what `mod.ts` re-exports: the client
  class + its options type, the error class + error-code registry, and the
  schema barrel. Internal helpers stay unexported.
- `exports` in `deno.json`/`package.json` should mirror this: `.` → `mod.ts`,
  `./schemas` → `schema/mod.ts`, and `./errors` → `errors/mod.ts`.

## Errors

Each connect owns exactly one error class extending `RESTlerError<M>` from
`@restler`, plus a `<CONNECT>ErrorCodes` registry object mapping an
`UPPER_SNAKE_CASE` code to a human-readable, `${template}`-interpolated
message (template variables are substituted from the `context`/metadata
object passed to the constructor). Throw with
`new <Connect>Error('CODE', metadata, cause?)`. Do not create one class per
failure mode — the code registry is the extension point, not the class
hierarchy. Place the `<Connect>Error` class in `errors/Base.ts`, its registry
in `errors/<Connect>ErrorCodes.ts`, and their test beside `Base.ts`; re-export
them through `errors/mod.ts` and the `./errors` subpath. Reuse documented vendor
error codes when they exist; otherwise define stable connect-specific codes
before throwing.

`RESTlerError`'s constructor is `(message: string, context?: M, cause?: Error)`
— read metadata back with the public `getContextValue<K>(key)`, never reach
into `.context` directly from outside the error class.

Every `<Connect>Error` exposes the resolved code as a public, readonly
`code: <Connect>ErrorCode` property, set after `super()` from the
fallback-normalized code actually used for the message template (so an
unregistered code passed in surfaces as `'UNKNOWN_ERROR'` on `.code`, not the
raw unrecognized string). This lets consumers branch on failure mode
programmatically — `if (err.code === 'RATE_LIMITED') { ... }` — without
resorting to `.message` substring matching.

## Configuration (Options pattern)

A connect's client class extends `Options<O, E>` from `@utils` (via
`RESTler<O>`, which itself extends `Options`) to store its config. `_getOption`
/ `_setOption` / `_getOptions` are **protected** — there is no public
`getOption`. If a value needs to be readable from outside the class, add a
named public getter that wraps `_getOption` internally:

```typescript
get baseCurrency(): string {
  return this._getOption('baseCurrency');
}
```

Never call `this.getOption(...)` — it doesn't exist on `Options`/`RESTler`.

### Credentials — always go through `auth: RESTlerAuth`

Never invent a bespoke top-level option for an API key/token/secret (no
`apiKey: string` sitting next to `baseURL`). Model every credential as the
standard `auth` option instead:

- Vendor uses HTTP Basic or Bearer auth → `{ type: 'BASIC', username,
  password }` or `{ type: 'BEARER', token, prefix? }`. The base
  `_authInjector` already emits the `Authorization` header for these — do
  **not** override `_authInjector` at all.
- Vendor authenticates some other way (a custom header, a query parameter,
  ...) → `{ type: 'CUSTOM', ...vendorFields }`. `RESTlerAuth`'s `CUSTOM`
  variant exists exactly for this — it carries arbitrary fields the subclass
  interprets itself. Override `_authInjector(endpoint)`, call
  `super._authInjector(endpoint)` first (preserves validation and any
  BASIC/BEARER handling on the same instance), then inject the vendor-specific
  header/query param from `this._getOption('auth')`.

This keeps every connect's credential surface identically shaped
(`options.auth`), gets free config-time validation (`RESTlerConfigError` if
`auth.type` isn't one of the three), and never silently drops a consumer's
auth config the way a full `_authInjector` override without `super()` would.

## Schemas

All request/response validation goes through `@guardian`. Build object
schemas directly with `Guardian.object({...})` — there is **no**
`GuardianProxy` wrapper in current Guardian; `Guardian.object(...)` already
returns an `ObjectGuardian<...>` you can call `.parse()`/`.safeParse()` on,
compose with `.optional()`, `.transform()`, `.passthrough()`, and unions where
the vendor documents multiple response variants. Model documented fields,
constraints, and optionality precisely; use `.passthrough()` only when the
vendor permits additional fields. Apply `.describe()` to schemas and important
fields so documentation can be generated from the schema. Every schema file
exports the schema object (`<Thing>SchemaObject`) and its inferred type
(`<Thing>Schema`) together, and is covered by a matching `.test.ts` that
validates accepted and rejected payloads.

The exported schema object always carries an explicit `BaseGuardian<T>`
annotation, never a bare `Guardian.object({...})` left to infer its own type —
JSR's slow-types check requires the originating declaration of any type
reachable from the public API to be explicit, and an exported object can't
usefully infer its type from itself (circular). Get that explicit type one of
two ways:

- Build the schema as a private, unexported intermediate const, infer
  `<Thing>Schema` from it via `GuardianInfer<typeof _thing>`, then export the
  schema object separately with the `BaseGuardian<<Thing>Schema>` annotation
  (see `connectors/s3/schema/ListObjects.ts` for the full pattern, including
  a nested example).
- Or, when the shape is simple enough (or needs hand-tuned JSDoc per field),
  hand-write `<Thing>Schema` directly as a `type` and annotate the exported
  `Guardian.object({...})` with it (see
  `connectors/discord/schema/Message.ts`'s `DiscordUserSchema` for an example
  with the reasoning spelled out in a comment).

Either way, `schema/mod.ts` re-exports every schema + type — that barrel is
what `mod.ts` re-exports under `./schemas`.

A flat `schema/<Thing>.ts` per file (the default shown in the layout above)
is fine while the surface is small. Once a connect has enough schemas that a
flat list stops being scannable, split `schema/` into subfolders — either by
role (`schema/request/`, `schema/response/`, `schema/common/`) or by
endpoint (`schema/<endpoint>/`) depending on which one actually groups
related types together for that vendor's API shape. Whichever you pick,
`schema/mod.ts` still re-exports the full flattened barrel, and imports
between the new subfolders go through each subfolder's own `mod.ts` (same
barrel-vs-direct-sibling rule as above, one level deeper).

## HTTP client

A connect's client class extends `RESTler<Options>` from `@restler` and sets
a `public readonly vendor` name. `RESTlerOptions.baseURL` is the only
required client-level option; every call to `this._makeRequest<T>({...})`
requires `method` (`RESTlerEndpoint`'s `method` field is mandatory, not
optional) — body-less methods (`GET`/`HEAD`/`OPTIONS`/`DELETE`) need only
`method`, others may add `contentType`/`payload`. `RESTler` throws
`RESTlerConfigError`/`RESTlerRequestError`/`RESTlerTimeoutError` (all
`RESTlerError extends BaseError`) — a connect's own error class wraps these
as the `cause` rather than re-declaring the same failure modes.

### Vendor error mapping goes through `_responseHandler`, not a hand-rolled method

`_makeRequest` already has a dedicated seam for translating a vendor's
HTTP-status/error-envelope conventions into the connect's own error class —
use it instead of writing a private `__handle(resp, schema)` method that
every endpoint method has to remember to call. Set a connect-wide default
once, after `super()` in the constructor:

```typescript
this._responseHandler = (response) => {
  if (response.status < 400) return response.body; // let 2xx (and any non-error status) through
  throw this.__toError(response); // maps status + body to a <Connect>Error
};
```

It runs on every response — including error statuses and empty bodies —
after the body is already parsed. **Throw** a `<Connect>Error` to signal a
failure (thrown `RESTlerError` subclasses surface unwrapped); **return** the
value the request resolves to on success — `response.body` unchanged, or an
unwrapped vendor envelope (`{ data, error } -> data`). As of
`@tundralibs/restler@1.1.3` this return value is load-bearing, not
informational: `_makeRequest` overwrites `response.body` with whatever the
handler returns, so a handler that forgets to `return response.body` on the
success path silently turns every successful response into `undefined`. Only
when one specific endpoint's response handling genuinely differs from the
connect-wide default (a status code that means something different on that
one endpoint), pass a `responseHandler` as `_makeRequest`'s second argument —
it overrides `_responseHandler` for that call only, entirely (the two never
compose).

### Validating a success body goes through `responseSchema`, via a shared `__requestAndValidate` wrapper

Because `_responseHandler` already turned every error response into a throw,
each endpoint method's remaining job is: call `_makeRequest`, validate the
(now known-successful) body against that endpoint's response schema, and
return the typed result. Do this with `_makeRequest`'s `responseSchema`
option — `(data) => guard.parse(data)` — instead of a separate `.safeParse()`

- manual branch after the call. `responseSchema` throws automatically on
  failure (as a generic `RESTlerResponseValidationError`, not any particular
  connect's error class), so wrap it in one private per-connect helper that
  maps that back onto `<Connect>Error` — every connect throws exactly one
  error class, response-validation failures included:

```typescript
private async __requestAndValidate<B>(
  endpoint: RESTlerEndpoint,
  guard: BaseGuardian<B>,
): Promise<B> {
  try {
    const resp = await this._makeRequest(endpoint, {
      responseSchema: (data) => guard.parse(data),
    });
    return resp.body as B;
  } catch (err) {
    if (err instanceof RESTlerResponseValidationError) {
      throw new <Connect>Error('RESPONSE_ERROR', {
        responseError: (err.cause as GuardianError | undefined)?.toJSON(),
      }, err);
    }
    throw err; // RESTlerTimeoutError/RESTlerConfigError/a <Connect>Error from _responseHandler pass through unchanged
  }
}
```

Name it `__requestAndValidate` (not `__request` — `RESTler` itself already
reserves a private `__request`, and TypeScript rejects a subclass redeclaring
it even at a different visibility). An endpoint method then shrinks to
building the request and delegating the rest:

```typescript
public async sendMessage(
  options: SendMessageRequestSchema,
): Promise<MessageSchema> {
  const [error, payload] = SendMessageRequestSchemaObject.safeParse(options);
  if (error || !payload) {
    throw new <Connect>Error('REQUEST_VALIDATION_ERROR', {
      reason: error?.message ?? 'validation failed',
      responseError: (error as GuardianError | null)?.toJSON(),
    });
  }

  return await this.__requestAndValidate(endpoint, MessageSchemaObject);
}
```

`B` is inferred from `guard` — no more manually writing
`_makeRequest<SomeType>(...)`. `.parse()`, not `.safeParse()`, is correct
inside `__requestAndValidate` — `responseSchema`'s contract is "throw on
failure," which `.parse()` already does; reaching for `.safeParse()` there
just re-introduces the tuple-branch-throw boilerplate this pattern exists to
remove.

Any method that can throw before the first `await` — including local
Guardian validation of the request, as above — MUST stay `async` with
`return await this.__requestAndValidate(...)`, not bare
`return this.__requestAndValidate(...)`. A synchronous throw from a
non-async method that returns a `Promise` bypasses `.catch()`/`await`'s
try-catch entirely, becoming an unhandled exception instead of a promise
rejection. Only a method whose entire body is the single delegating call,
with no validation that can throw first, may safely omit `async` (an `async`
method with no `await` is itself a lint error, so it cuts both ways).

Not every endpoint needs this — a response validated from **headers**
instead of the body (e.g. an object-storage `PUT` returning its `etag` via
an `x-amz-version-id`-style header, not a JSON body) or with no body to
validate at all (a `DELETE` returning `204`) calls `_makeRequest` directly,
unchanged. `responseSchema` only ever sees `response.body`.

## Imports

- Use the shared root import aliases (`@restler`, `@guardian`, `@asserts`,
  `@test`) — do not add a competing alias for the same dependency inside a
  connect's own `deno.json`. Dependencies needed by only one connect belong in
  that connect's manifests and use an `@`-prefixed alias (for example,
  `@utils`).
- One import statement per module; merge value and type imports
  (`import { Guardian, type GuardianInfer } from '@guardian'`).
- Doc examples (README, JSDoc `@example`) use the public specifier
  (`@tundraconnect/<connect>`), never a relative path.

## Runtime target

Every connect must run unmodified on **Deno, Bun, and Node** (CI matrix), and
should avoid runtime-specific APIs so it also works in **Cloudflare Workers**
and the **browser** even though those aren't in CI yet: stick to `fetch`,
`URL`, `crypto.subtle`, and other standard Web APIs; never import
`node:*`/`Deno.*` APIs directly in a connect's implementation.

## Naming & style

- Files/classes: `PascalCase.ts`. Barrels/helpers: `camelCase.ts` or
  `mod.ts`. Folders: lowercase or kebab-case.
- Privacy prefixing mirrors the TS modifier: `public` → no prefix,
  `protected` → `_one`, `private` → `__two`.
- Module-level constant lookup tables: `UPPER_SNAKE_CASE`.
- JSDoc: `{@link}` for non-builtin types, `@throws` on every throwing method,
  one `@example` per exported symbol where practical.
- Formatting/lint are enforced by `deno fmt`/`deno lint` (root `deno.json`) —
  don't hand-format against them.

## Tests

- Prefer live tests against the vendor when credentials and a stable sandbox or
  test endpoint are available. Keep secrets out of source and skip those tests
  when the required environment is absent. When live testing is unavailable,
  mock `@restler`'s transport or use captured fixtures instead.
- **Live tests are a `describe` block appended to the connect's existing
  `<Connect>.test.ts`** — after the mock suite, same file, same `@test`
  import, never a separate file. Read env vars with `envArgs()` from
  `@utils` (already aliased in every connect); gate on every credential the
  connect needs being present, and restrict actual execution to one runtime
  so a local dev running `deno task test && bun test && npm run test:node`
  back-to-back only fires the real call once, not three times:
  ```typescript
  import { envArgs } from '@utils';

  const env = envArgs();
  const credentials = { apiKey: env.get('CONNECTOR_<NAME>_API_KEY') };
  const liveTestsEnabled = Object.values(credentials).every((v) => !!v);

  describe({
    name: '<Connect> — live',
    ignore: !liveTestsEnabled,
    bun: false,
    node: false,
    fn: () => {
      it('...', async () => {/* real call against the vendor */});
    },
  });
  ```
  `describe`'s options form takes a **single** options object
  (`describe({ name, fn, ignore, bun, node, ... })`) — there is no
  `describe(name, options)` two-argument overload. A mutating call
  self-cleans in a `try`/`finally` (`putObject`/`deleteObject`,
  `saveObject`/`deleteObject`, ...) wherever the vendor supports an inverse;
  where no inverse exists but the object only ever appears in the vendor's
  own test-mode/sandbox dashboard (Stripe, Razorpay, PayPal), leaving it
  behind is fine — say so in a comment. Never live-test an operation that
  needs an interactive step this repo can't automate (e.g. capturing a
  payment requires a real checkout) or that would mutate real, undo-less
  state on a live account (e.g. Sentry's `updateIssue`) — exclude it with a
  one-line comment explaining why, don't force it.
- **`LIVE_TEST_ALLOW_VISIBLE_EFFECTS`** additionally gates any live call
  whose side effect is real-world-visible with no way to undo it (an actual
  chat message, SMS, or call — e.g. Discord/Telegram/ntfy/Twilio's send
  methods, and Slack's `postMessage`, which is still briefly visible before
  its own `deleteMessage` cleanup runs): `ignore: !liveTestsEnabled ||
  !env.get('LIVE_TEST_ALLOW_VISIBLE_EFFECTS')`. Never set on the automatic
  monthly CI schedule (`.github/workflows/live-tests.yml`) — only locally,
  or via that workflow's manual `workflow_dispatch` opt-in.
- Env var names follow `CONNECTOR_<NAME>_<FIELD>` (uppercase, connect name
  with `-` → `_`) — see `.env.sample` for the full, current list per
  connect, including any extra test-resource var a connect needs (e.g.
  `CONNECTOR_S3_TEST_BUCKET` for a bucket that must already exist — a live
  test can't safely create and tear down a whole bucket/container in a
  normal run).
- One `.test.ts` per source file, co-located.
- Import `describe`/`it` (+ `beforeAll`/`afterAll`/`beforeEach`/`afterEach`)
  from `@test` — this resolves to `@tundralibs/compat/test`, which
  dispatches to `@std/testing/bdd` (Deno), `bun:test` (Bun), or `node:test`
  (Node) so the same test file runs unmodified on all three. It does **not**
  re-export assertions — always import those separately from `@asserts`.
- Use the options form to skip per-runtime/OS, don't branch on a runtime
  global: `it({ name: '...', node: false, fn: () => {...} })` rather than
  `if (RUNTIME === 'node') return;`. Same options shape works on `describe`.
- Only pull in runtime-neutral Compat subpaths that a connect actually needs.

## Versioning & releases

Versions, tags, and `CHANGELOG.md` entries are owned by **release-please** —
never hand-edit a version number or changelog. A PR's squash-merge commit
message must be a Conventional Commit; the scope is the connect's directory
name.

## Cryptography and identifiers

Use the shared root aliases `@crypt` (`@tundralibs/crypt`) and `@id`
(`@tundralibs/id`) — never hand-roll a primitive they provide:

- Hashing, HMAC, RSA/EC/Ed25519 signing and verification, JWT issue/verify,
  and the constant-time comparison every signature check needs come from
  `@crypt` (`sha256`, `signHMAC`/`verifyHMAC`, `signRSA`, `verifyEC`,
  `ecdsaDerToRaw`, `issueJWT`, `constantTimeEqual`, …).
- Generated identifiers — idempotency keys, client-side ids — come from
  `@id` (`ulid`, `cuid2`, `nanoID`, …).

Raw Web Crypto (`crypto.subtle`) or a third-party primitive is acceptable
only where `@crypt` cannot express the operation, and the call site must
say why in a comment. Known cases: an HMAC keyed by _decoded bytes_ with
base64 output (S3 SigV4's chained derivation, Azure Shared Key, Polymarket
L2, Standard Webhooks) — `signHMAC` takes a text key and returns hex;
and Keccak-256 / secp256k1 (Polymarket, via `@noble`).

Two related rules with no gap behind them. Base64/hex encoding of
arbitrary bytes comes from the shared `@encoding` alias (`@std/encoding` —
`encodeHex`, `decodeHex`, `encodeBase64`, `decodeBase64`, …); never
hand-roll a codec. `@crypt` does emit base64 where that is the natural
output of its own operation (`signRSA`, `sha256(…, 'base64')`), but it
ships no standalone codec and `signHMAC` is hex-only — re-encode with
`@encoding` rather than by hand. And UUID v4, where a vendor mandates it
(Kalshi's `client_order_id`), is `crypto.randomUUID()` — the platform
primitive is the sanctioned choice, not a gap in `@id`.

## Rate limits

Do not parse `Retry-After`-style headers in a connect. RESTler (>= 1.3.0)
owns that: read the hint with `this._parseRetryAfter(response.headers)` in
`__toError` and attach it as `retryAfterSeconds` on the `RATE_LIMITED`
error. A caller opts into RESTler's single retry with `maxRetryWait`; when
that retry is exhausted (or the hint exceeds the cap) RESTler throws
`RESTlerRateLimitError` _before_ `_responseHandler`, so `__requestAndValidate`
must rewrap it as the connect's own `RATE_LIMITED` (with `retryAfterSeconds`
and `retried`) — every connect still throws exactly one error class.
